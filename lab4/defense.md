# Ответы на вопросы по архитектуре и методологии тестирования проекта

### 1. Какая у нас архитектура тестирования?

**Ответ:**
В данном проекте реализована **трехуровневая изолированная архитектура тестирования**, построенная по принципу "пирамиды тестирования". Архитектура разделена на три независимых пакета (модуля), каждый из которых отвечает за свой слой верификации приложения:
1. **Пакет модульного тестирования (`test.publicmethods`):** Нижний, самый массивный слой. На каждый публичный метод структуры данных `CustomList` выделен отдельный Java-класс (шаблон `ListИмяМетодаTest`). Это гарантирует атомарность сред и исключает взаимное влияние тестов друг на друга.
2. **Пакет нагрузочного тестирования (`test.performance`):** Изолированный слой для оценки вычислительной и пространственной сложности. Он управляет жизненным циклом очистки памяти JVM и замеров времени работы алгоритмов сортировки на разных порядках размерностей.
3. **Пакет интеграционного/приемочного UI-тестирования (`test.gui`):** Верхний слой автоматизации. Использует специализированный робот-манипулятор для имитации действий реального пользователя над графическими панелями Swing.

Для предотвращения хрупкости тестов (эффекта *Raw Type* и затирания дженериков Java до уровня `Object`) архитектура полностью опирается на **строго типизированные Mock-заглушки классов** (`MockLinearTraversal`, `MockSortStrategy`), вынесенные в контекст тестовых файлов.

### 2. Какие бывают виды тестирования и в чём различия (Нагрузочное, Unit, Интеграционное)?

**Ответ:**
Различия между тремя видами тестирования, примененными в лабораторной работе, заключаются в их целях, объектах проверки и изолированности:

| Критерий сравнения | Юнит-тестирование (Unit Testing) | Интеграционное тестирование (Integration / GUI) | Нагрузочное тестирование (Performance / Load) |
| :--- | :--- | :--- | :--- |
| **Что является объектом проверки?** | Один изолированный публичный метод или класс (например, `add`, `remove`, `swap`). | Взаимодействие нескольких связанных модулей (Бизнес-логика + Память + GUI Swing). | Эффективность работы алгоритма при росте объемов входных данных. |
| **Какая главная цель?** | Доказать, что алгоритм метода работает логически верно во всех штатных и краевых ситуациях. | Доказать, что при клике на кнопку интерфейса данные правильно передаются в СД и выводятся на экран. | Оценить вид зависимости трудоемкости (времени) и памяти (кучи) от размерности СД (\(N\)). |
| **Зависимость от внешнего окружения** | **Нулевая**. Все внешние зависимости подменяются заглушками (Mock-объектами). | **Высокая**. Зависит от потока обработки событий ОС (EDT), фокуса окон и отрисовки менеджеров компоновки. | **Высокая**. Зависит от спецификации процессора, текущего состояния и проходов сборщика мусора JVM (GC). |

### 3. Какие у нас используются фреймворки?

**Ответ:**
Для автоматизации сборки и прогона тестов в проекте используется стек из трех дополняющих друг друга инструментов:
*   **Gradle (версии 9.x / 8.x):** Автоматизированная система сборки (Build Tool). Отвечает за компиляцию тестов, управление внешними зависимостями из репозитория Maven Central, управление кэшем конфигурации, изоляцию процессов тестирования и автоматическую генерацию сводных интерактивных HTML-отчетов.
*   **JUnit 5 (Jupiter):** Основной фреймворк для написания и структурирования тестов. Предоставляет движок запуска (`Test Engine`), механизмы параметризации и ассерты (`Assertions`) для проверки логических утверждений.
*   **AssertJ Swing (версии 3.17.1):** Специализированный UI-фреймворк. Предоставляет низкоуровневых роботов-манипуляторов (`FrameFixture`) для безопасного управления потоком выполнения графического интерфейса (EDT), программной симуляции кликов мыши по кнопкам, ввода текста в поля `JTextField` и считывания логов вывода.

### 4. Какие у нас используются в коде аннотации junit и зачем они нужны, как работают и т.д.?

**Ответ:**
В нашем коде используются следующие ключевые аннотации JUnit 5:

*   **`@Test`**
    *   *Зачем нужна:* Помечает метод как тестовый.
    *   *Как работает:* Движок JUnit Jupiter сканирует классы при помощи рефлексии (Reflection API), находит методы с этой аннотацией и принудительно вызывает их. Если метод завершается без исключений — тест считается пройденным (`PASSED`).
*   **`@BeforeAll`**
    *   *Зачем нужна:* Выполняет глобальную конфигурацию среды один раз перед запуском *всех* тестов в классе.
    *   *Как работает:* Метод обязан быть статическим (`static`). В `ApplicationGuiTest` мы используем её для вызова `FailOnThreadViolationRepaintManager.install()`, что мгновенно блокирует любые попытки Swing отрисовать компоненты вне безопасного графического потока EDT еще до старта тестов.
*   **`@BeforeEach`**
    *   *Зачем нужна:* Выполняет код инициализации перед *каждым* отдельным тестовым методом.
    *   *Как работает:* Сбрасывает состояние окружения. В юнит-тестах она используется для создания "чистого" объекта `new CustomList<>(3)`, а в GUI-тестах — для разворачивания нового чистого фрейма `JFrame` в потоке EDT. Это гарантирует, что тесты не влияют на результаты друг друга.
*   **`@AfterEach`**
    *   *Зачем нужна:* Выполняет очистку ресурсов (teardown) после *каждого* теста.
    *   *Как работает:* Гарантирует выполнение даже в случае падения теста. В `ApplicationGuiTest` через метод `window.cleanUp()` она принудительно закрывает окно фрейма и освобождает фокус мыши робота операционной системы, предотвращая утечки памяти и блокировку экрана.
*   **`@DisplayName("...")`**
    *   *Зачем нужна:* Задает понятное, читаемое имя для теста на английском/русском языке.
    *   *Как работает:* Подменяет техническое название метода (например, `testAddSingleElement`) на красивую строку в дереве сборщика Gradle и в итоговом HTML-отчете.

### 5. Какие есть кейсы в тестировании, граничные случаи и т.д.?

**Ответ:**
В рамках тестирования структуры данных были разработаны три категории тест-кейсов (сценариев):

1.  **Стандартные случаи (Happy Path / Позитивные тесты):**
    Проверка работы методов в идеальных условиях. 
    *   *Примеры:* добавление элемента в пустую ноду, последовательное чтение `get(0)`, `get(1)`, inplace-замена значения через `set()`.
2.  **Граничные / Краевые случаи (Boundary Value Analysis):**
    Тестирование поведения алгоритма на крайних физических и логических границах диапазонов:
    *   *Индекс `0` (Нижняя граница):* Вставка в начало (`insert(0)`) или удаление самого первого элемента (`remove(0)`), проверяющие корректный перенос указателя `head` на новую ноду.
    *   *Индекс `size - 1` (Верхняя граница):* Удаление последнего элемента списка, проверяющее сдвиг указателя `tail` на предыдущую ноду.
    *   *Переполнение блока памяти (`Block Capacity`):* Вставка элемента в позицию внутри полностью заполненного массива, проверяющая каскадный перенос (`carry`) последнего элемента ноды в автоматически созданную следующую ноду.
    *   *Опустошение ноды:* Удаление последнего оставшегося элемента из блока, проверяющее, что метод `remove` полностью занулил ноду (`null`), уменьшил `nodeCount` и корректно перестроил ссылки, предотвращая утечки памяти.
    *   *Минимальная конфигурация:* Создание списка с минимально возможным размером блока `new CustomList<>(1)`.
3.  **Негативные / Ошибочные случаи (Error Handling):**
    Проверка устойчивости СД к некорректным действиям пользователя:
    *   Обращение к отрицательному логическому номеру (`get(-1)` или `remove(-1)`).
    *   Обращение к несуществующему индексу, равному или большему размера списка (`get(size)`).
    *   Попытка установить некорректную вместимость блоков (`setBlockCapacity(0)` или `-5`).
    *   Передача пустых ссылок (`null`) вместо предикатов поиска или стратегий сортировки.
    Во всех этих случаях тесты проверяют генерацию правильных системных исключений (`IndexOutOfBoundsException`, `IllegalArgumentException`, `NullPointerException`) через метод `assertThrows`.
