# Архитектурное описание пакета `test.publicmethods`

**Назначение пакета:** Изолированное модульное тестирование (Unit Testing) всех открытых интерфейсов и методов кастомной блочно-связанной структуры данных `CustomList`. Пакет обеспечивает верификацию корректности работы алгоритмов управления памятью, inplace-модификаций, условной фильтрации и механизмов экспорта данных.

### Архитектурные принципы и методология тестирования
Проектирование тестовых сценариев внутри пакета опирается на принципы атомарности, изоляции и полноты покрытия граничных условий:

* **Принцип атомарной декомпозиции (Single Responsibility Component):** 
  Каждый публичный метод структуры данных тестируется в строго выделенном, отдельном классе (шаблон `ListИмяМетодаTest`). Это гарантирует независимость тестовых сред, исключает взаимное влияние побочных эффектов и позволяет мгновенно локализовать сбойный узел структуры данных при падении сборки.
* **Метод граничных значений (Boundary Value Analysis):**
  Для каждого метода, помимо стандартных сценариев использования (Happy Path), спроектированы тесты для критических состояний и экстремальных входных данных. Включает проверку отрицательных индексов (`-1`), выход за верхний предел (`index >= size`), корректность перестройки внутренних ссылок (`head` / `tail`) при полном опустошении структуры, а также обработку `null`-параметров.
* **Верификация каскадных изменений внутренней памяти:**
  Архитектура тестов учитывает блочную специку `CustomList` (массивы фиксированной емкости внутри связанных узлов `Node`). Тестовые сценарии методов `insert` и `remove` проверяют не только логическую последовательность элементов, но и физическое состояние структуры: корректность выделения новых блоков при переполнении, каскадный перенос элементов (`carry`) между соседними массивами и автоматическое уничтожение (`deallocation`) пустых нод для предотвращения утечек памяти.
* **Изоляция от эффекта стирания типов (Anti-Raw-Type Architecture):**
  Для тестирования перегруженных методов, использующих функциональные интерфейсы (`Predicate`, `ForEachCallbackInterface`, `TraverseStrategyInterface`), вместо гибких, но нестабильных анонимных лямбда-выражений применены строго типизированные статические классы-заглушки (`Mock-объекты`). Это предотвращает сброс generic-типов Java до уровня `Object` на этапе компиляции и защищает сборщик от конфликтов кэширования конфигурации.

### Структура и компоненты пакета
Пакет расположен в изолированной директории `src/test/java/test/publicmethods/` и разделен на следующие функциональные тест-модули:
* **Модули структурных модификаций (`ListInsertTest`, `ListRemoveTest`, `ListClearTest`, `ListAddTest`):** Проверяют корректность изменения топологии списка, сдвиги элементов влево/вправо и полную очистку.
* **Модули inplace-модификаций (`ListSetTest`, `ListSwapTest`, `ListGetTest`):** Тестируют доступ на чтение/запись по логическому индексу и быстрый взаимный обмен элементов в памяти без изменения общего размера структуры.
* **Модуль динамической реконфигурации (`ListSetBlockCapacityTest`):** Верифицирует алгоритм полной перестройки и перераспределения элементов по новым внутренним массивам «на лету» при смене емкости блоков.
* **Модули поиска и обхода (`ListFirstThatTest`, `ListFirstIndexThatTest`, `ListForEachTest`):** Проверяют работу предикатов линейного поиска и последовательную итерацию элементов.
* **Модули экспорта данных (`ListToArrayListTest`, `ListGetBlocksTest`):** Проверяют выгрузку внутреннего состояния СД во внешние коллекции, включая двумерную матрицу блоков для GUI-компонентов (`JTable`).
