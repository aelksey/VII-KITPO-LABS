Ниже предоставлен контекст проекта, требования лабораторной, описание архитектуры и исходный код.

### 1. ТРЕБОВАНИЯ И ВАРИАНТ ЗАДАНИЯ
* Вариант структуры данных (СД): Вариант 8 — "Список с массивом ссылок в каждом элементе". Каждый узел (Node) содержит массив ссылок Node<E>[] next. Базовые сквозные операции (add, get, remove, iterate) выполняются по 0-му (базовому) индексу этого массива (current.next).
* Вариант типа данных (ТД): Вариант 8.1 — "2D-точка, сравнение по расстоянию от начала координат (sqrt(x^2 + y^2))".
* Дополнительное требование: Обеспечить поддержку как минимум двух типов данных (реализованы Point2D и Integer).
* Критическое ограничение (Open-Closed Principle): Добавление нового ТД должно происходить исключительно путем создания класса нового ТД, реализующего общий интерфейс, и регистрации его экземпляра в фабрике. Изменять код существующей структуры данных, вьюшки (GUI) или фабрики при добавлении ТД запрещено.

### 2. АРХИТЕКТУРА И ПРИМЕНЕННЫЕ ПАТТЕРНЫ
Проект спроектирован на Java с использованием Generics и строго разделен по пакетам (слоям):
1. Пакет `ru.nstu.app.types` (MODEL): 
   - `UserType<T>` — generic-интерфейс билдера типа данных. Инкапсулирует имя типа, методы фабрикации (create, clone), парсинг строки (parseValue), потоковое чтение (readValue), сериализацию объекта в файл (writeValue) и сравнение (compare).
   - `Point2D` и `Point2DType` — сущность точки и её билдер (Вариант 8.1).
   - `UserIntegerType` — второй обязательный тип для демонстрации полиморфизма.
   - `UserFactory` — фабрика билдеров. Хранит статический список `List<UserType<?>> builders`. Для добавления нового ТД строка добавляется только сюда.
2. Пакет `ru.nstu.app.sort` (STRATEGY):
   - Применен паттерн "Стратегия" (Strategy) для алгоритмов сортировки. Сортировки меняются на лету.
   - `SortStrategy` — общий интерфейс алгоритма.
   - `QuickSortStrategy` и `MergeSortStrategy` — конкретные реализации умных алгоритмов O(N log N).
   - `SortFactory` — фабрика для выбора стратегии сортировки в GUI.
3. Пакет `ru.nstu.app.serialize` (STRATEGY):
   - Применен паттерн "Стратегия" для форматов сохранения файлов (меняются на лету).
   - `SerializeStrategy` — интерфейс для сохранения/загрузки.
   - `JsonTxtSerializeStrategy` — текстовый построчный формат.
   - `BinarySerializeStrategy` — собственный бинарный формат данных (DataOutputStream/DataInputStream).
   - `SerializeFactory` — фабрика форматов файлов.
4. Пакет `ru.nstu.app.core` (DATA STRUCTURE):
   - `CustomList<T>` — generic-структура данных Варианта №8. Полностью очищена от бизнес-логики. Она ничего не знает о конкретных типах данных, алгоритмах сортировки и форматах файлов. Она лишь управляет узлами и массивом ссылок, а тяжелые задачи делегирует внешним стратегиям и билдерам, передаваемым в параметры методов (`sort(SortStrategy, UserType)`, `save(SerializeStrategy, UserType)`).
5. Пакет `ru.nstu.app.view` (VIEW):
   - `MainFrame` — GUI на Java Swing. Работает со списком и билдером через абстрактный тип `Object` (`CustomList<Object>`, `UserType<Object>`), получая их динамически из фабрик на основе выбора пользователя в JComboBox. Это обеспечивает полную независимость UI от внутренней логики.

### 3. ПРАВИЛА ДЛЯ ДАЛЬНЕЙШЕЙ РАБОТЫ (ИНСТРУКЦИЯ ДЛЯ LLM)
Если я попрошу тебя исправить ошибку, написать тест или добавить фичу, ты обязан:
1. НЕ ломать generic-архитектуру. Не скатываться к жесткому касту типов `(Point2D)` внутри `CustomList` или `MainFrame`. Все операции должны выполняться через методы интерфейса `UserType<Object>`.
2. Строго соблюдать Вариант 8 структуры данных: использовать `Node.next` для итерации и связей.
3. Помнить про предотвращение утечек ресурсов: любой ввод-вывод (IO) должен быть обернут в `try-with-resources`.
4. Не менять код ядра, если задача касается только добавления нового типа данных или нового алгоритма — используй расширение через фабрики и стратегии.
